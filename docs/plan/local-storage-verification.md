# Проверка локального хранения индекса — #13

Технический сценарий, а не реализация индекса. Он не читает заметки, не отправляет HTTP-запросы и не записывает файлы хранилища. Используется renderer IndexedDB; файлового fallback нет. База проверки отделена от будущей базы индекса.

## Воспроизведение

1. Выполнить `npm run build`, установить `main.js`, `manifest.json`, `styles.css` в `.obsidian/plugins/obsidian-ai-helper/` двух настольных хранилищ, перезагрузить плагин.
2. В палитре выполнить **Проверить локальное хранение индекса** / **Check local index storage**. Нажать **Прочитать и проверить**: в новом хранилище ожидается отсутствие данных.
3. В первом хранилище нажать **Записать 6 МиБ**. Ожидается `6291456 байт / 96 блоков` и имя базы. Запись заменяет только предыдущие синтетические данные этой проверки.
4. Полностью завершить Obsidian через Quit (перезагрузки окна недостаточно), запустить заново, повторно открыть команду и нажать чтение. Ожидается `6291456 / 96`; каждый байт проверяется.
5. Во втором хранилище до записи ожидается отсутствие данных, имя базы должно отличаться. Записать данные во втором, очистить первый, убедиться, что второй по-прежнему читается. Очистить второй. Проверить отсутствие данных в обоих.
6. Нажать **Проверить имитацию ошибок**. Ожидаются обработанные ошибки недоступного API (передан отсутствующий IndexedDB), превышения предела приложения и намеренно отменённой настоящей транзакции записи. Это не проверка фактического заполнения диска.
7. Сравнить содержимое файлов до/после; проверить `git status --short` и отсутствие файлов с пробными данными в хранилище. В DevTools → Application → IndexedDB проверить базу с префиксом `obsidian-ai-helper-storage-probe-v1-`.
8. Для оценки квоты выполнить в Console `await navigator.storage.estimate()`. Это оценка общего origin, а не гарантированная ёмкость конкретной базы. При любой неожиданной ошибке или потере данных результат не считать успешным; вернуть выбор хранения на согласование, не переходить к файлам.

Открывать одну проверку на хранилище и дожидаться завершения операции перед следующей. Закрытие диалога не отменяет начатую запись. При прерывании процесса до записи маркера завершения чтение не объявляет частичные данные сохранёнными; повторная запись или очистка удаляет их. Очистка удаляет записи, небольшая пустая база остаётся в IndexedDB.

## Идентификация, объём и память

- Идентификатор — SHA-256 абсолютного пути из публичного `FileSystemAdapter.getBasePath()`, с префиксом плагина и версией сценария. Имя хранилища недостаточно: разные пути с одинаковым именем изолированы. Путь не сохраняется в базе. Перенос/переименование пути означает новую идентичность и последующее перестроение; восстановление после переноса не обещается.
- Синтетическая нагрузка — 6 МиБ; жёсткий предел этого сценария — 8 МиБ. Это не предел поддержки заметок и не замер размера будущего embedding-индекса.
- Запись и проверка идут последовательно блоками до 64 КиБ, без `getAll` и полной копии данных в JS. Транзакции закрываются между блоками, соединение закрывается после операции. Это способ ограничивать рабочие буферы; реальный максимум RSS/внутренних буферов Chromium не измерен. Для будущего индекса использовать порционные операции и ограниченный кеш, измерить память на больших хранилищах в #24.
- Открытие и транзакция имеют таймаут 5 секунд; blocked/open errors, отмена записи и повреждение данных дают явный результат ошибки. Квота/диск остаются ограничением окружения; ошибка транзакции не запускает запись в файл.

## Фактические результаты

Команда плагина запускалась через Console Obsidian (`app.commands.executeCommandById('obsidian-ai-helper:local-storage-probe')`); действия выполнялись кнопками диалога, результаты наблюдались в renderer. Проверки типов не использовались как свидетельство доступности IndexedDB.

Во время управления через UI два нажатия Enter попали в редактор заметки вместо Console. Добавленные две пустые строки удалены через Obsidian API; итоговое совпадение всех 1061 файлов проверено по SHA-256. Сам сценарий не обращается к API записи заметок.

Автоматические результаты: `test/note-search.test.ts` проверяет восстановление на новом экземпляре, изоляцию разных путей с одинаковым именем, независимость очистки, недоступный API, предел объёма и отменённую запись. Подмена — только внешняя граница IndexedDB (`fake-indexeddb`); это не настоящий Obsidian и не проверка перезапуска процесса. Полный Vitest: **16 файлов / 160 тестов**, production build с typecheck проходит.

LM Studio не использовался: этот сценарий не получает embeddings и не проверяет поиск или качество источников. Фактическое исчерпание дисковой квоты, большие индексы, RSS и долговременная сохранность после обновления/очистки профиля приложения не проверены. До завершения проверки второго хранилища локальный вариант не объявляется полностью подтверждённым.
