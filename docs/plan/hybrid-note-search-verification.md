# Совмещение смыслового и текстового поиска — #20

## Поведение и начальные параметры

`createNoteSearch.searchSources(question, signal?, budgetBytes?)` отбирает несколько актуальных фрагментов по всему разрешённому индексу. `search()` сохраняется как совместимый способ получить первый источник. Заголовок, путь, цепочка разделов, `tags`, `aliases` и тело уже входят в сохранённый текст фрагмента: новый формат индекса и переиндексация не нужны.

Поиск сочетает косинусное сходство с совпадениями целых Unicode-терминов без учёта регистра, нормализованных NFKC. Подстрока идентификатора не является точным совпадением. Служебные слова EN/RU исключаются из текстового запроса. Начальные правила: смысловой порог **0,45**, полное совпадение значимых терминов либо минимум два совпадения при покрытии от **60%**; точные идентификаторы с цифрами, `_` или `-` учитываются также внутри длинного вопроса, в том числе когда разные идентификаторы записаны в отдельных заметках. Текстовое свидетельство допускает источник ниже смыслового порога и добавляет **2 × покрытие** к оценке отбора; вес идентификаторов зависит от доли найденных идентификаторов вопроса. Показываемое пользователю «Сходство» остаётся косинусным, а не объединённой оценкой. Описание настройки порога уточнено на EN/RU.

Контекст содержит до **6 фрагментов**. Независимый общий предел — **12000 UTF-8 байт** сериализованных источников с учётом экранирования внутри сообщения HTTP JSON. Чат дополнительно уменьшает этот бюджет на полную историю, системную инструкцию, текущий вопрос, резерв ответа (по умолчанию **1024**) и **256** единиц протокольного запаса. Используется прежняя консервативная оценка «один байт — один токен». Не помещающиеся фрагменты пропускаются; если не помещается ни один подходящий фрагмент, показывается ошибка бюджета, история сохраняется.

Повторы тела независимо от названия заметки удаляются: точные нормализованные копии и близкие копии с пересечением пятисловных последовательностей от **80%** (Jaccard); разные числовые значения/идентификаторы и порядок их первого появления сохраняются. Дополняющий большой фрагмент не удаляется только из-за включения короткого. Все ветви используют один и тот же отбор допустимых, совместимых и свежих заметок. Перед передачей модели источники повторно проверяются.

Найденные данные передаются модели только для текущего запроса. Чат показывает каждый использованный фрагмент и ссылки `[1]`…`[6]`; открытие и предпросмотр проходят проверку актуальности. При отсутствии сведений генерация не запускается. Инструкция модели требует явно обозначать отсутствующие части ответа и запрещает заполнять пробелы общими знаниями.

## Сценарий повторной ручной проверки Obsidian

1. Собрать `npm run build`, обновить `main.js`, `manifest.json`, `styles.css` в установленном плагине и перезагрузить Obsidian.
2. Скопировать контрольные заметки в разрешённую тестовую папку, построить индекс и включить поиск в чате. Порог — 0,45. Выполнить четыре первых вопроса таблицы: проверить источники, отсутствие генерации для погоды и явный пробел для времени прибытия.
3. Выполнить вопросы `авторизация`, `Ошибка доступа`, `Доступ`: проверить текстовые совпадения. Для демонстрации независимой текстовой ветви временно установить смысловой порог 1 и спросить про `ERR_AUTH_42`; после вернуть 0,45.
4. Скопировать «Доступ» под другим названием: ответ не должен показывать повторяющиеся фрагменты. Добавить новую заметку с другим полезным сведением об `ERR_AUTH_42`: она должна дополнить ответ. Проверить открытие ссылок и раскрытие каждого использованного фрагмента.
5. Изменить исходную заметку без переиндексации или исключить её папку: старый фрагмент не должен передаваться модели и открываться как актуальный источник. Проверить небольшой контекст и длинную историю: сообщение о бюджете либо набор помещающихся полезных источников, без сокращения истории.
6. Переключить язык EN/RU: проверить описание порога и отображение нескольких источников.

Статус обязательной ручной приёмки #20: **успешно**, отдельно от автоматических тестов и API-прогона LM Studio.

## Исправление восстановления при запуске — 2026-10-12

Пользователь сообщил о потоке уведомлений «Локальное хранение индекса недоступно», пустом индексе и `InvalidStateError: Failed to read the 'result' property from 'IDBRequest': The request has not finished`.

Выявлены две причины:

- Снимок индекса собирался в обработчике `get("updates").onsuccess`, который читал `.result` соседних bulk-запросов. Это воспроизведено на границе IndexedDB с отложенной готовностью результата ключей; позиция в production-бандле соответствовала присланному стеку. Снимок теперь собирается после завершения всей транзакции, а исключение при сборке результата отклоняет публичный запрос вместо необработанного исключения.
- При начальном обнаружении файлов Obsidian посылает `create`/`modify`. Обработчики плагина запускали чтения индекса до `onLayoutReady`, создавая поток операций и тайм-аутов. Регрессионный сценарий со 100 начальными событиями вызывал 104 открытия базы. Теперь обработка `create`/`modify`/`delete` начинается после готовности хранилища; начальное восстановление сверяет сохранённый индекс с полным актуальным набором заметок. Последующие события по-прежнему обрабатываются.

Регрессии проверяются через публичные `restore()`/`search()` и жизненный цикл плагина с IndexedDB/событиями хранилища на границах: `test/indexeddb-restoration.test.ts`, `test/index-startup.test.ts`. Формат базы не менялся; индекс не удалялся и не перестраивался ради исправления.

Ручная проверка в настоящем Obsidian 1.14.4 на открытом хранилище пользователя: после установки исправления и перезагрузки поток уведомлений исчез; включение поиска показало **100% — 403 / 403**, «Индексация завершена». Существующий индекс восстановлен без перестроения. Временные диагностические сообщения удалены из исходного кода.

Итоговые проверки исправления: **30 файлов / 383 теста Vitest — успешно**; `npm run build` с TypeScript и production-бандлом — успешно. Независимое ревью относительно `1fab9e4`: **Standards — 0 замечаний; Spec — 0 замечаний**.
