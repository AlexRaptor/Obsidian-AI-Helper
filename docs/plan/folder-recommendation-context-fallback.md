# Будущие задачи: рекомендация папок при нехватке контекста

Статус: пункт 1 реализован для LM Studio; пункты 2–7 отложены. Реализация автоматического перехода отменена в текущей работе. Автоматические проверки и сборка пройдены; пользователь подтвердил прохождение ручной проверки в Obsidian.

Задачи расположены в предлагаемом порядке приоритета: сначала уточнить реальную нехватку контекста, затем добавить относительно простой отбор папок и улучшить его охват, после этого решить ограничения длинных заметок и расширить сценарии использования. Приоритет не означает обязательную последовательность: обработка длинных заметок и проверка всех папок могут развиваться независимо от embedding-отбора.

## Задачи по приоритету

1. **Более точный подсчёт токенов — реализация для LM Studio.** Проверять размер запроса с учётом выбранной модели, инструкций, данных и резерва ответа. Это позволит реже отклонять запросы, которые фактически помещаются, из-за консервативной оценки по размеру UTF-8. При отсутствии подходящего способа подсчёта сохранять консервативную проверку. Область первой реализации: разбор заметок, поиск папок и смешанный поиск в чате. [Описание и критерии приёмки](prompt-token-counting.md). Поддержка других модель-серверов остаётся будущей задачей.

2. **Подбор среди близких папок через embeddings.** Сравнивать заметку с описаниями всех допустимых папок, отбирать кандидатов в пределах бюджета и передавать модели диалога полную заметку, полные описания кандидатов и правила родителей. Рассмотреть автоматический переход при нехватке контекста обычного разбора; отдельный режим был первоначальной альтернативой, а не дополнительной обязательной функцией. Показывать причину перехода, применённый вариант и число папок, проверенных моделью диалога, относительно общего допустимого набора. Предупреждать, что подходящая папка могла остаться вне выборки. Этот вариант помогает при большом объёме описаний, но не решает проблему слишком длинной заметки.

3. **Расширение выборки при неоднозначности.** Если подбор близких папок не дал подходящего варианта или выявил спорные результаты, проверять следующие группы кандидатов. Сохранять результаты предыдущих проверок, обновлять число рассмотренных папок и ограничивать количество запросов. Зависит от задачи 2; повышает охват, но не гарантирует проверку всех папок.

4. **Разбор длинной заметки по частям с объединением выводов.** Когда сама заметка не помещается в контекст, анализировать её частями и затем объединять выводы для рекомендации папок. Сохранять основания из всех частей, учитывать несколько тем, противоречия и общую цель заметки. Подходит для длинных заметок, которые нельзя обработать одним запросом даже после сокращения набора папок.

5. **Поэтапная проверка всех папок группами.** Разделять описания папок на группы, проверять каждую группу отдельно и затем сопоставлять рекомендации. Сохранять правила родителей и основания решений. Это вариант для полного охвата без отсечения по смысловой близости; он потребует большего количества запросов и не решает отдельно проблему слишком длинной заметки.

6. **Предварительное резюме длинной заметки.** Сначала готовить компактное представление заметки, затем использовать его для рекомендации папок. Сохранять цель, статус и факты, важные для критериев включения и исключения; явно показывать, что использовано резюме. Для текста, не помещающегося даже в запрос на резюме, потребуется обработка по частям. Этот вариант оставлен ниже разбора по частям из-за риска потери деталей, влияющих на выбор папки.

7. **Подбор кандидатов в чате.** Распространить отбор папок на советы о размещении будущей заметки и поиск папок в диалоге. Учитывать намерение пользователя, историю сообщений и совместное использование поиска заметок и папок. Показывать причину ограничения выборки и число рассмотренных папок. Для embedding-отбора использовать механизм задачи 2, адаптировав его к вопросу пользователя вместо существующей заметки.

## Общие требования к будущим решениям

- Решение о перемещении заметки принимает пользователь.
- Сохраняются критерии включения и исключения, правила родителей и объяснение явных конфликтов.
- Частичный охват обозначается явно: отсутствие подходящей папки в выборке не означает её отсутствия во всём хранилище.
- Причину выбора способа обработки и фактический охват формирует плагин, а не модель диалога.
- Учитываются актуальность заметки и описаний, отмена, доступность моделей и правила отправки данных на настроенные серверы.

Увеличение окна контекста и сокращение описаний пользователем также обсуждались как способы выполнить обычный полный разбор. Это существующие пользовательские действия, а не отдельные задачи реализации.
