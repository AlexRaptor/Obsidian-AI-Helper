# Протокол перевода #58

## Воспроизведение и проверенные варианты

Первоначальный протокол требовал копирования маркеров Markdown. В ответе на
«How to take notes» все ID p1–p19, p21–p23 были на месте; p20 — локальное
встраивание. Но модель теряла защищённые элементы:

```text
p4: Прочитайте ⟦AIH0:p4:0⟧, связанную заметку⟦AIH0:p4:2⟧ и полезные ссылки⟦AIH0:p4:4⟧.
p7: Записывайте важные идеи⟦AIH0:p7:0⟧, примеры⟦AIH0:p7:3⟧ и устаревшие советы⟦AIH0:p7:5⟧.
p21: Короткая справка помогает читателю.
p23: Стабильный блок ссылок.
```

Проверка правильно запрещала запись. Усиление промпта не устраняло зависимость
от копирования маркеров. В первом прототипе разметка осталась локально, но
каждый текстовый промежуток переводился независимо. Реальная проверка
17 октября 2026 выявила слишком мелкое дробление:

| ID первого прототипа | Оригинал | Ответ модели |
| --- | --- | --- |
| `p1~6` | `The ` | `Результаты` |
| `p1~7` | `results` — подпись ссылки | пробел |
| `p1~12` | ` and ` между кодом и формулой | пробел |

Смысл подписи перенесён в другой слот. Разрешение пустых значений оставило бы
ссылку без подписи; перенос соседнего слова обратно в ссылку был бы
угадыванием. Этот ответ зафиксирован и отклоняется в интеграционных тестах.

Второй прототип переводил строку целиком и возвращал отдельные точные цитаты
с ID и номером вхождения для оформления. Локальная сборка проверяла цитаты,
вложенность и общие границы. На `qwen/qwen3.8-27b` первый запуск прошёл, но
повторения выявили несовпадающий падеж цитаты, исключение ссылки из родительского
выделения и добавление Markdown. Один ограниченный исправляющий запрос помогал
не всегда. Вариант отвергнут: модель фактически писала две копии одних слов,
которые требовалось согласовать. Без ограничения JSON и обязательных ключей
ответ часто вообще терял подпись, а исправление находилось среди недоверенных
данных запроса вместо отдельной системной инструкции. Увеличивать число исправлений не стали.

## Выбранный интерфейс: целый перевод и обязательные точные подписи

Мелкие текстовые промежутки не переводятся отдельно. Запрос содержит целую
строку `text`, её исходное дерево `parts` и метаданные каждого объекта
оформления: роль, исходную фразу, родителя и общие границы. Обычный текст
не имеет ID; артикль может исчезнуть без пустой обязательной подписи.

В предпочтительном ответе модель сначала формирует связный полный перевод,
затем дословно копирует из него подписи для каждого объекта:

```json
{"units":[{"id":"p1","text":"Результаты надёжны.","labels":{
  "a0":{"text":"Результаты","occurrence":1}
}}]}
```

`occurrence` — номер точного вхождения цитаты в полном переводе, начиная с 1.
Регистр, окончания и пробелы не нормализуются. Независимые оформленные фразы
могут менять порядок. Для строки без объектов возвращается `labels:{}`.

ID содержит уникальный номер и краткую исходную подпись для сопоставления
моделью; проверка использует его как непрозрачный ключ. Пример выше сокращён.
Подпись видимого объекта должна соответствовать его собственной исходной
фразе. Родительская цитата должна содержать дочернюю; соседние объекты не
могут пересекаться. При исходном совпадении границ обязательны `sameStartAs`
и `sameEndAs`; блок с `atEnd` обязан завершать строку.

Защищённые значения заменены в исходном тексте обычными описаниями
(`inline code`, `mathematical expression`). Модель может перевести эти слова
в полном тексте, затем скопировать точную цитату в подпись защищённого ID.
Локальная сборка заменяет именно этот диапазон настоящим значением. Код,
формулы, цели ссылок, свойства и встраивания не отправляются; цели встраиваний
не читаются.

Завершающие сноски и идентификаторы блоков с однозначной позицией вне
оформления полностью исключаются из запроса и восстанавливаются локально
в исходном порядке вместе с разделителями. Сноска внутри фразы или внутри
выделения остаётся объектом протокола; её позиция не угадывается.

Модель не распределяет обычный текст по обязательным слотам. Полный перевод
остаётся единственным источником обычных слов; точные подписи назначают
оформление. Объект `labels` содержит обязательное поле для каждого ID в
динамической JSON schema: отсутствие ссылки может запрещаться уже грамматикой
генерации. Простое дерево в массиве не давало такой гарантии: модель
повторяемо пропускала отдельный объект, несмотря на инструкции и исправление.
Первый вариант с цитатами не имел обязательных ключей схемы и такой проверки
исправления; его неуспех не скрывается в истории экспериментов.

Внутреннее представление сборки — типизированное дерево `parts`: строки
обычного текста, `type:text` с вложенными частями и `type:keep` с обычным
описанием. Декодер также принимает эту строго проверяемую форму ответа;
неоформленная единица может использовать компактное `id/text`. Если одновременно
приходят `labels` и `parts`, ответ отклоняется. Предпочтительная схема требует
именно `id/text/labels` и не содержит альтернативной формы.

## Структура и проверка

Каждый исходный ID единицы и объекта должен присутствовать ровно один раз.
Пропуск, дубль, чужой ID, неверный тип, лишнее поле, пустой перевод единицы или
видимой подписи, смена родителя, рассогласование общих границ, новая разметка
или повреждённый Unicode блокируют запись. Обычные текстовые строки могут
сливаться, переставляться и исчезать при изменении грамматики; это не пустые
переводы обязательных объектов. Объекты `keep` не считаются переведённым текстом.

Пересечение диапазонов не представимо корректным деревом, а вложенность
дополнительно сверяется с оригиналом. При исчезновении артикля вложенные
оболочки могут охватить одно слово, например `**The [results]**` →
`**[Результаты]**`: сохраняются и ссылка, и выделение. Повторяющиеся слова
различаются положением объекта в дереве, без поиска похожих слов в переводе.

Точные цитаты ищутся только в полном переводе, без похожести или исправления
регистра. Из проверенных диапазонов строится типизированное дерево; обычные
промежутки берутся из полного текста. Повторы ключей JSON проверяются до
принятия, поскольку JSON.parse иначе молча оставляет последнее значение.
Проверенный ответ превращается в локальное представление. Каждый защищённый
токен оригинала обязан присутствовать ровно один раз. Сопоставление идёт по
идентичности токена, а не его позиции в массиве: допустима перестановка целых
оформленных участков. Локальная сборка не придумывает потерянные объекты и не
перемещает перевод между ними. Прежняя проверка непустоты каждого промежутка
заменена проверкой целого перевода и обязательных текстовых объектов.
Проверки токенов, блочной структуры и зависимостей сохраняются.

Полный перевод и части сравниваются точно. Допустим один определённый случай:
если все обязательные объекты на месте, части совпадают с началом полного
перевода и исходная строка заканчивается обычным непустым текстом, оставшееся
окончание берётся дословно из полного перевода вне оформления. Это не поиск
похожих слов и не восстановление пропущенной подписи. Другие расхождения
отклоняются. Эта совместимая форма не используется предпочтительной схемой labels.
Окончание проходит ту же проверку Unicode, управляющих символов
и новой разметки. При отсутствии завершающей пунктуации, которая была в
исходной фразе, ответ также отклоняется; это узкая структурная проверка,
а не доказательство смысловой полноты.

Разбор серий `*`/`_` различает открытие и закрытие, включая вложенный жирный
текст внутри курсива и ограничение сумм длин серий, кратных трём; правила
описаны в [CommonMark §6.2](https://spec.commonmark.org/0.31.2/#emphasis-and-strong-emphasis).
Границы `*`/`_` проверяются по правилам flanking с учётом восстановленного
синтаксиса и защищённых значений: подчёркивание внутри слова не должно
терять роль выделения, а соседний код не должен ошибочно считаться буквами.


Пробелы на границах оформленных объектов — локальная компоновка. Если модель
соседними частями склеила два слова, а исходная граница разделялась пробелом,
сборка восстанавливает разделитель. Место границы уже задано деревом; слова
не подбираются и не переставляются. Внутри исходного слова (`pre**fix**`)
пробел не добавляется. Текст и знаки пунктуации модель формирует сама.

Внутренние переносы дают отдельные ID строк (`p1/l1`, `p1/l2`); оригинальные
переносы, отступы и синтаксис остаются локально. Когда позволяет бюджет,
соседние строки находятся в одном запросе. Раздел и предыдущие принятые пары
служат вспомогательным контекстом. При делении длинной строки часть сохраняет
смещение в неизменном оригинале; вложенное оформление может продолжаться
через части. Пустые строки на границе разреза не передаются модели;
переносы и крайние открывающие/закрывающие токены сохраняются локально. Дерево диапазонов индексируется один раз на строку, без
многократного попарного поиска при обходе частей.

## Бюджет, ошибки и ограниченные повторы

Счётчик/оценка учитывает сериализованные текст, дерево, метаданные и контекст.
Полный контекст и дерево увеличивают вход. Ответ дублирует полный перевод
для сверки, что увеличивает стоимость и вероятность обрезания; существующее
уменьшение частей учитывает это через фактический finishReason и бюджет. При малом бюджете сначала убирается
вспомогательный контекст; необходимые части дерева сохраняются.

Обязательная инструкция протокола идёт после стилевого промпта пользователя.
При ошибке допускается **один** исправляющий запрос для текущей группы:
исходные единицы, предыдущий ответ и безопасное описание нарушения с известным
ID. Инструкция исправления передаётся отдельным системным сообщением; исходник,
разрешённые ID и сравниваемые значения остаются данными, а не инструкциями. Он повторно считается в бюджете; если не помещается, не отправляется.
Второй неверный ответ останавливает операцию. Ограничение не сбрасывается
при уменьшении той же попытки. Существующие три уменьшения при обрезании и
переполнении сохраняются. Бесконечных исправлений нет.

Для перевода передаётся необязательный `response_format.type=json_schema`:
динамическая схема требует полный `text`, допустимый ID единицы и все ID
подписей в `labels`, непустой текст и целое положительное вхождение каждой
цитаты; посторонние поля запрещены. Схема не доказывает точность перевода,
совпадение цитат или правильность диапазонов — это проверяется локально.
Используется
[документированный формат LM Studio](https://lmstudio.ai/docs/developer/openai-compat/structured-output).
При явном отказе от JSON schema (HTTP 400/422 или ошибка протокола до начала
содержимого) клиент один раз убирает формат и запоминает это для пары
сервер/модель. Отказ streaming тоже даёт один переход к обычному ответу;
оба флага меняются только в сторону отключения, максимум три транспортных
вызова на chat. Авторизация, rate limit и HTTP 500 не вызывают JSON fallback.
Остановка и политика ожидания общие для всех попыток; обычный чат формат
перевода не получает.

Принятые группы и прогресс не меняются при отклонении новой группы. Снимок
ADR-0004, остановка (в том числе исправления), непрерывное неполное начало,
арбитраж с чатом, безопасная запись и повтор только открытия используют
существующую операцию. Ошибки на русском/английском показывают вид нарушения
и известный ID, включая скрытое окно. Неизвестные ID модели не отражаются
в интерфейсе. Пользователь может явно продолжить или завершить операцию.

## Прототип, проверка и ограничения

Интеграционные тесты проходят через команды/меню и действия операции. Они
покрывают четыре фразы пользователя, исчезновение артикля, вложенное оформление,
перестановку фраз, повторяющиеся подписи, полную статью, сотни оформленных
участков с делением, все поддерживаемые конструкции и повреждённые ответы.

Настройки реальной модели читаются из указанного пользователем `data.json`,
без вывода ключей. Окно 65536 задано пользователем отдельно. Прогон использует
настоящую `NoteTranslation` и клиент с реальной сетью; хранилище и области
моделируются в памяти, без открытия или изменения пользовательского vault.
Воспроизводимый запуск и результаты: [сценарий #58](../testing/note-translation/issue58.md).

Практический фокус проверки — русский, английский и основные европейские
языки. Универсальное качество всех языков не заявляется. Для смешанной
фразы правило явно требует перевести чужие слова и сохранить только слова,
уже написанные на целевом языке.

Ограничения: правильное дерево не доказывает семантическую точность текста.
Модель может потребовать исправления и всё равно вернуть ошибку; после
ограниченной попытки сохранение блокируется. Защищённые значения скрыты, поэтому
их конкретная семантика недоступна модели. Границы строк и деление по бюджету
могут ограничивать согласованность; качество любой модели не гарантируется.
